# 任务对象与模式切换

用于维护会话中穿插试写、泛称检查/优化，或已发生“用户要改工作流却交改稿”的偏离。只决定当前操作和交付对象，不自动要求展示模式表、创作账本或确认问题。

## 先分对象，再取知识

| 当前要求 | 操作与交付 |
|---|---|
| 设计故事、生成提示词 | 采用角色/事件/观看安排，交完整作品 |
| 明确修改这版提示词、交新版 | 在获准范围修作品，交完整修订 |
| 检查或查原因，未授权修稿 | 给实际问题、证据、原因与改法 |
| 优化技能/工作流、修执行顺序 | 从失败样本定位缺口，修改安装来源、相关功能映射，验证并同步；交文件改动与证据 |
| 明确同时优化成文与工作流 | 修订获准作品并完成适用复查，同时修改负责失败的安装来源、映射并验证同步；两项各自交付，不以其中一项代替另一项 |

选择依据按顺序为：当前明确修改对象 → 会话中尚有效的对象约定 → 其余上下文。用户最新消息优先，但“看着优化”没有明确新对象，不能凭它撤销之前的维护约定。助手刚刚生成的稿、自己提出的改稿计划或“我会调整时长”的进度消息不提供用户授权。

创作或已授权改稿中的交付前检查，不是一个另需修稿授权的“只检查”任务；应在交付前修完已发现问题并复查。用户询问“检查了没/为什么没检查完”时先回答实际执行情况，不把该问句当作取消仍有效创作/修复授权；明确“只检查、不改”才限制为检查结论。不能用这一分支为此前带错交稿辩解。

在维护会话里，用户请生成一个例子时完成该轮例子；下一次泛称“检查/优化”回到已约定的维护对象。明确说“就改刚才这版，给完整新版”则该轮改作品。既不能让维护约定挡住明确创作，也不能让试写擦掉维护约定。单独普通创作会话里，对“这份稿”提出检查修复按作品处理，不把所有“优化”强行变成技能维护。

## 维护分支在编译之前结束

对象与修改范围分别判断：明确“优化这份稿”指作品，但“只改摄影”仍限定职责；明确“优化工作流”指来源，但“只修声音模块”不授权重构所有板块。用户已授权全面优化时可修实际相关依赖，不为每项可逆修订反复确认。按[专项联用边界](functional-collaboration.md)区分继承事实、可修改部分和需要报告的上游冲突。

识别为维护后，先核安装入口及真正负责该失败的来源。角色错配修角色选择/取库；镜号齐全但看点不成立修观看设计/验收；剧情代价没有必要修关键结果与能力检查；请求对象漂移修任务路由。不要先生成新稿，再把新稿说成工作流已优化。

当前作品可用于审查因果与定位规则缺口，不能因此自动改角色、时长或正文。维护所需行为回归用隔离测试验证对应范围；普通路由回归可以只输出任务对象与首个操作，不必写另一段完整剧情。

## 对重复偏离的处理

前一版已有“不得重写”却仍重写，先查规则是否放在创作路由之后、是否缺少泛称/试写继承规则、检查是否只看文件和字面句子。修位置、分支和实际回归；不只再追加一次“必须落实”。记录实际验证层级：源文件结构/链接/ZIP、人工反例审查、独立路由选择、完整出稿、成片观察各自只证明其范围。

若用户纠正对象，立即停止错误分支并按新明确对象执行；不以“已经开始检查稿件”为理由继续交新版。
